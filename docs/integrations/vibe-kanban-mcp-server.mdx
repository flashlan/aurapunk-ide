Vibe Kanban exposes a local MCP (Model Context Protocol) server, allowing you to manage projects, issues, workspaces, and repositories from external MCP clients like Claude Desktop, Raycast, or even coding agents running within Vibe Kanban itself.

<Note>
This page covers connecting **external MCP clients** to Vibe Kanban's MCP server. For configuring MCP servers **within** Vibe Kanban for your coding agents, see the [MCP Server Configuration](/integrations/mcp-server-configuration) guide.
</Note>

<Info>
Vibe Kanban's MCP server is **local-only** - it runs on your computer and can only be accessed by applications installed locally. It cannot be accessed via publicly accessible URLs.
</Info>

## Setting Up MCP Integration

### Option 1: Using the Web Interface

This works if you're adding the Vibe Kanban MCP server to any [supported coding agent](/supported-coding-agents) **within** Vibe Kanban.

1. In Vibe Kanban Settings, navigate to the "MCP Servers" page
2. In the "Popular servers" section, click on the Vibe Kanban card
3. Click the `Save Settings` button

<Frame>
<img src="/images/vk-mcp-server-config.png" alt="MCP Servers configuration page showing how to add Vibe Kanban MCP server" />
</Frame>

### Option 2: Manual Configuration

You can manually add the MCP server to your coding agent's configuration. The exact syntax will depend on your coding agent or MCP client.

Add the following configuration to your agent's MCP servers configuration:

```json
{
  "mcpServers": {
    "aurapunk": {
      "command": "npx",
      "args": ["-y", "aurapunk-ide@latest", "--mcp", "--mode", "global"]
    }
  }
}
```

`--mcp` launches the local MCP stdio server. Any additional arguments after `--mcp` are passed through to the `aurapunk-mcp` binary.

## Available MCP Tools

The Vibe Kanban MCP server provides tools for managing projects, issues, workspaces, and task execution.

<Note>
Many tools accept an optional `project_id` parameter. When running inside a workspace linked to a project, it is inferred automatically from context and can be omitted.
</Note>

### Context

| Tool | Purpose | Required Parameters | Optional Parameters | Returns |
|------|---------|-------------------|-------------------|---------|
| `get_context` | Get current workspace context (only available within an active workspace session) | None | None | Project, issue, and workspace metadata |

### Project Operations

| Tool | Purpose | Required Parameters | Optional Parameters | Returns |
|------|---------|-------------------|-------------------|---------|
| `list_projects` | List projects | None | None | List of projects with IDs and names |

### Project Statuses

Card statuses are the board columns of a project. Cards reference them by ID, so
create or adjust a project's statuses before setting a card's status. The SDLC
preset gives a project a ready-made workflow board.

| Tool | Purpose | Required Parameters | Optional Parameters | Returns |
|------|---------|-------------------|-------------------|---------|
| `list_project_statuses` | List a project's card statuses (board columns) | None | `project_id` | Statuses with IDs, names, colours, order, hidden and terminal flags |
| `create_project_status` | Create a card status in a project | `name`<br/>`color` | `project_id`<br/>`sort_order`<br/>`hidden`<br/>`is_terminal` | Created status |
| `update_project_status` | Update a card status (rename, recolor, reorder, hide, or change its terminal flag) | `status_id` | `name`<br/>`color`<br/>`sort_order`<br/>`hidden`<br/>`is_terminal` | Updated status |
| `delete_project_status` | Delete a card status | `status_id` | None | Deletion confirmation |
| `inject_sdlc_statuses` | Inject the SDLC preset (planning, development, testing, review, iteration, deployment) into a project | None | `project_id` | Number of columns added plus the project's full column set |

### Issue Management

| Tool | Purpose | Required Parameters | Optional Parameters | Returns |
|------|---------|-------------------|-------------------|---------|
| `list_issues` | List issues in a project | None | `project_id`<br/>`status`<br/>`priority`<br/>`search`<br/>`simple_id`<br/>`parent_issue_id`<br/>`tag_id`<br/>`tag_name`<br/>`sort_field`<br/>`sort_direction`<br/>`limit`<br/>`offset` | Paginated list of thin summary rows: `id`, `simple_id`, `title`, `status`, `updated_at`, plus `priority`/`parent_issue_id`/PR fields only when set. Never the description; null fields are omitted - use `get_issue` for detail. |
| `create_issue` | Create a new issue | `title` | `project_id`<br/>`description`<br/>`priority`<br/>`parent_issue_id` | Created issue ID |
| `get_issue` | Get detailed issue information | `issue_id` | None | Full issue details with tags, relationships, sub-issues, and PRs |
| `update_issue` | Update an existing issue | `issue_id` | `title`<br/>`description`<br/>`status`<br/>`priority`<br/>`parent_issue_id` | Minimal ack: `id`, `simple_id`, `status`, `status_id`, `updated_at`, `changed[]`, plus echoes of the changed fields. Never the description body (only `description_chars`) - use `get_issue` for the card body. |
| `delete_issue` | Delete an issue | `issue_id` | None | Deletion confirmation |
| `list_issue_priorities` | List allowed priority values | None | None | List of priorities: urgent, high, medium, low |

<Tip>
For `update_issue`, the `parent_issue_id` field supports three states: omit it entirely to leave the parent unchanged, pass `null` to un-nest the issue from its parent, or pass a UUID to set a new parent. The response is a minimal acknowledgement rather than the full issue: its `changed[]` list names the fields you supplied, so an applied un-nest appears as `"parent_issue_id": null` with `"parent_issue_id"` in `changed[]`, while an untouched parent omits the key entirely. Call `get_issue` when you need the issue body back.
</Tip>

### Project Memory (mem0)

The project-memory tools give coding agents shared, cross-session memory backed by
one of two selectable adapters. `mem0_vk` is the existing self-hosted service
(default `http://localhost:8000`, override with `MEM0_URL`); `mem0_platform` uses
the official Mem0 Platform API. The `user_id` is the repository slug, so every
CLI working in the same repository — opencode, Claude, and so on — reads and
writes the same memory within the selected backend.

Type `/memory` in the workspace chat to open Settings → Memory. There you can
enable/disable the memory endpoints, switch adapters, select local versus shared
self-hosted Mem0, and save the Mem0 API key. Qdrant URL/API key and embedding
dimensions apply only to `mem0_vk`; Mem0 Platform manages those dependencies.
Credentials are stored in `~/.vibe-kanban/memory.toml` with restricted local
permissions and are returned to the UI only as a saved/not-saved flag.

#### Memória por projeto

Each repository has its own memory namespace, identified by its repository slug
(`user_id`). A fact saved while working on `aurapunk-ide` is not returned while
working on another repository. This keeps decisions, conventions, architecture
notes, and lessons from one codebase out of another. Different agents and
sessions can share the same project memory as long as they use the same adapter
and slug.

Memory is intentionally agentic: the agent calls `memory_search` before
analysing a relevant area and calls `memory_save` only for verified, durable
facts after work is complete. It is not an automatic dump of every conversation
and it does not replace `AGENTS.md`, which remains the canonical project
instruction file.

#### Reconstrução após mudanças no código

`mem0_vk` records the Git `commit_sha` associated with a saved fact when the
workspace context is available. `memory_check_staleness` can then compare that
commit with the current worktree and report evidence when the referenced code
was removed. This means an agent can treat an old memory as **possibly stale**
instead of blindly trusting it.

When graph extraction was unavailable when older facts were saved,
`mem0_vk` also provides a re-extraction operation. It scans the existing facts,
runs the configured extraction model again, rebuilds entity/relation payloads,
and updates the project graph. This reconstructs the memory structure; it does
not restore deleted source code or prove that a fact is still true.

Mem0 Platform performs extraction and graph processing as a managed, asynchronous
operation for new imports. Its internal graph is not the same as the
`mem0_vk` graph contract, so the custom traversal, Git staleness check, and bulk
re-extraction controls are currently available only when `mem0_vk` is selected.

### Migrating project memory

Changing the adapter does not move memories. `mem0_vk` and Mem0 Platform use
different stores, identifiers, extraction pipelines, and graph implementations.
The Memory settings screen therefore provides a separate, preview-first
migration operation. It reads one repository slug at a time, compares normalized
memory content with the destination, and skips duplicates. It never deletes the
source and it never persists the migration credentials.

The safe procedure is:

1. Keep the current adapter active and run a **Preview** for the repository.
2. Review `would_migrate`, `skipped_duplicates`, and any warnings.
3. Run **Execute migration** with the explicit confirmation checkbox.
4. Wait for the destination queue to finish. Mem0 Platform imports are
   asynchronous and return an event for background processing.
5. Search the destination and verify representative memories before switching
   the active adapter in Settings.

Migration is content-idempotent: repeating it does not intentionally create a
second copy of the same normalized fact. It does not preserve the original
vector, Platform/internal graph IDs, or the exact extraction result. The
destination re-extracts each fact using its own configured pipeline. When a
`commit_sha` is available, it is copied as metadata; `mem0_vk` can use it for
its Git staleness check, while Mem0 Platform treats it as ordinary metadata.

The backend endpoint used by the UI is `POST /api/usage/memory-migration`.
Its request contains `source`, `destination`, `user_id`, `mode` (`preview` or
`execute`), and `confirm`. Source and destination API keys are accepted only
for that request and are never returned.

| Tool | Purpose | Required Parameters | Optional Parameters | Returns |
|------|---------|-------------------|-------------------|---------|
| `memory_search` | Search the project's shared memory for facts relevant to a query | `query`<br/>`user_id` | None | Ranked memory list |
| `memory_recall` | Fetch all memories stored for the project | `user_id` | None | Full memory list |
| `memory_save` | Persist a verified, durable fact to the project's memory | `content`<br/>`user_id` | None | Confirmation |
| `memory_graph_traverse` | Traverse related graph entities from a named start node | `start`<br/>`user_id` | `hops`<br/>`direction` | Nodes and relations (`mem0_vk` only currently) |
| `memory_check_staleness` | Check whether a graph entity may have become stale since its saved commit | `user_id`<br/>`entity` | None | Commit and evidence (`mem0_vk` only currently) |

<Tip>
Use `memory_search` **before** analysing code to recall decisions, conventions and
lessons the project already learned. Save only **verified, self-contained facts**
with `memory_save` — never speculation, so future agents do not pick up false
memories. All three tools are best-effort: they return empty results (or
`stored: false`) when the mem0 server is unreachable, and never block work.
</Tip>

### Workspace Sessions

| Tool | Purpose | Required Parameters | Optional Parameters | Returns |
|------|---------|-------------------|-------------------|---------|
| `start_workspace` | Create a workspace and start its first coding-agent session | `name`<br/>`executor`<br/>`repositories` | `prompt`<br/>`variant`<br/>`issue_id` | Workspace ID |
| `create_session` | Create a session in an existing workspace | None | `workspace_id`<br/>`executor` | Session summary |
| `list_sessions` | List sessions for a workspace | None | `workspace_id` | Session list |
| `run_session_prompt` | Run a coding-agent prompt inside an existing session | `session_id`<br/>`prompt` | None | Execution details |
| `get_execution` | Inspect execution status and final message | `execution_id` | None | Execution details |

The `repositories` parameter is an array of objects with:
- `repo_id`: The repository ID (UUID)
- `branch`: The branch for this repository

When `issue_id` is provided, the workspace is automatically linked to the remote issue. If `prompt` is omitted, the linked issue's title and description are used as the workspace prompt.

## Using the MCP Server

Once you have the MCP server configured, you can leverage it to streamline your project planning and execution workflow:

1. **Plan Your Work**: Describe a large feature or project to your MCP client
2. **Request Issue Creation**: At the end of your description, simply add "then turn this plan into issues"
3. **Automatic Issue Generation**: Your MCP client will use the Vibe Kanban MCP server to automatically create structured issues in your project
4. **Start Workspaces**: Use `start_workspace` to programmatically begin work on issues with specific coding agents

## Example Usage

### Planning and Issue Creation

```
I need to build a user authentication system with the following features:
- User registration with email validation
- Login/logout functionality
- Password reset capability
- Session management
- Protected routes

Then turn this plan into issues.
```

Your MCP client will use the `create_issue` tool to break this down into individual issues and add them to your Vibe Kanban project automatically.

### Starting a Workspace Session

After issues are created, you can start work on them programmatically:

```
Start working on the user registration issue using Claude Code on the main branch.
```

Your MCP client will use the `start_workspace` tool with parameters like:
```json
{
  "name": "User registration with email validation",
  "executor": "claude-code",
  "repositories": [
    {
      "repo_id": "987fcdeb-51a2-3d4e-b678-426614174001",
      "branch": "main"
    }
  ],
  "issue_id": "123e4567-e89b-12d3-a456-426614174000"
}
```

This creates a new workspace, links it to the issue, generates a feature branch, and starts the coding agent in an isolated environment.

### Complete Workflow Example

```
1. List projects to find the project ID
2. List issues in the project filtered by status
3. Create a new issue for "Add user profile page"
4. Start a workspace session for the issue using Amp on the develop branch
```

Each step uses the appropriate MCP tool (`list_projects`, `list_issues`, `create_issue`, `start_workspace`) to manage the complete workflow from planning to execution.

### Internal Coding Agents (Within Vibe Kanban)

A powerful workflow involves using coding agents within Vibe Kanban that are also connected to the Vibe Kanban MCP server:

1. **Create a Planning Issue**: Create an issue with a custom agent profile configured with a planning prompt. See [Agent Configurations](/settings/agent-configurations) for details on creating custom profiles.
2. **Explore and Plan**: The coding agent explores the codebase and develops a comprehensive plan
3. **Generate Issues**: Ask the coding agent to "create a series of individual issues for this plan"
4. **Automatic Population**: The agent uses the MCP server to populate individual issues directly in the Vibe Kanban interface

This creates a seamless workflow where high-level planning automatically generates actionable issues in your project board.
