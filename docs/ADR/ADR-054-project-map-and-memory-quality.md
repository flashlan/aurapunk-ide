# ADR-054: Project map from the code, and quality rules for Mem0 writes

## Status

Accepted — implemented and deployed 2026-09-27 (mem0-vk on the memory LXC;
verified through the Cloud gateway).

## Date

2026-09-27

## Context

ADR-053 made the app push relevant memory to each new session. What it can
push is limited by what is stored, and the store was poor:

- The 49 memories of `aurapunk-ide` were mostly change-log notes ("Fix: …",
  "commit 0cff6fcc"), session reports ("Verificado: cargo check…"), open work,
  four duplicate pairs, and **fragments without a subject** ("NÃO usa o
  `MsgStore` global…"). The fragments come from `mem0-vk` itself: every write
  is split by an LLM into "facts", which drops the context that made them true.
- Nothing gave an agent a quick view of *where things live*, so it explored
  with `grep`/`read` or exploration agents.
- The operator's classifier (`jev`) is unreachable on that network, and the
  memory gate fails open — so nothing filtered the junk.

## Decision

1. **Project map, built from the code** (`services::project_map`): areas
   (crates, packages, `docs/ADR`) → modules, each with the first sentence of
   its `//!` doc and its main public items (TS: exported names per feature
   directory). Area descriptions come from the module doc, else the
   `Cargo.toml` / `package.json` `description` (added to every crate that had
   none), else `AGENTS.md`'s Project Structure. Nothing is generated by a
   model.
   - `project_map` MCP tool (`GET /api/project-map`): the tree of the agent's
     own worktree, overview by default, modules for a `path`.
   - Mem0 copy under `map-<repo>`: an overview entry plus one entry per area
     (split at ~1.5 KB), written verbatim. A manifest
     (`<config>/project-map/<repo>.json`) keeps each entry's hash and point
     id, so a refresh rewrites only changed areas (owner-scoped point
     deletes). Refreshed after merges (at most every 6 h) and by
     `refresh_project_map`. Session-start recall (ADR-053) also searches the
     map, so a new session learns where the relevant code lives.
2. **Quality rules for writes** (`rlcd::memory_lint`, deterministic, applied
   before the classifier): reject commit hashes, dates, change-log phrasing
   ("Fix:", "Verificado:", "committed"…), open work, texts that name no place
   in the code (path, file, code span, identifier), too short/long, and
   credentials. Calibrated on the stored memories: 18 of 49 rejected, none of
   the good ones. Every rejection returns how to rewrite
   (WHERE — WHAT/HOW — WHY, with an example). The classifier gains a
   `change_report` question. `memory_save` refuses near-duplicates (vector
   score ≥ 0.93) and asks `mem0-vk` for a **verbatim** write: one point with
   the text as written, graph extraction still running.
3. **`mem0-vk`** (source of truth: `aurapunk-ide/mem0-vk`, deployed at
   `/opt/mem0-vk` on the memory LXC): `verbatim` queued writes (one point, graph
   still fed), owner-scoped `DELETE /api/memories/{id}?user_id=`, and
   `GET /api/features` so clients check support first. Verbatim map and
   handoff entries use the existing `POST /api/memories/index` (no LLM, no
   graph, `source: direct_index`), which the Cloud gateway allows on every
   plan. The IDE only reads back `direct_index` entries, so extracted
   fragments are never used as a handoff.

## Consequences

- An agent can orient itself in one call (`project_map`) and new sessions
  arrive with the relevant map areas and facts.
- The map is only as descriptive as the code's docs: modules without `//!`
  docs show only their public items. Documenting modules improves the map
  directly.
- Existing low-quality memories stay until reviewed; with scoped deletes
  deployed they can be removed individually.
- First sync writes ~45 entries; later syncs only changed areas (Free plan:
  1,000 writes/month).
